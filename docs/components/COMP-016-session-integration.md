# COMP-016 — Project session integration and memory

**Status:** Implemented — verified on a scratch multi-repo workspace (2026-10-19); not yet observed in a live session
**Last updated:** 2026-10-19
**Source:** [`kit/.claude/rules/product-factory.md`](../../kit/.claude/rules/product-factory.md), [`cli/src/rules.rs`](../../cli/src/rules.rs), [`cli/src/memory.rs`](../../cli/src/memory.rs), [`cli/src/install.rs`](../../cli/src/install.rs), `/factory memory` in [`SKILL.md`](../../kit/.claude/skills/factory/SKILL.md)
**Decisions:** [ADR-010](../decisions/ADR-010-session-behaviour-and-memory.md)

## Purpose

Any Claude Code session in a factory-managed repo, or inside one module of a
factory-managed workspace, works through the factory without being told. What
Claude learns there ends up in git, not only in per-machine auto memory.

## Pieces

| Piece | Where | Loads | Effect |
|---|---|---|---|
| Always-on rule | `.claude/rules/product-factory.md` (root and every module) | Every session | Route change requests through `/factory`; answer questions directly; never touch the base branch; knowledge goes to git; `pf` must be on PATH |
| Skill trigger | `when_to_use` in `SKILL.md` frontmatter | Skill listing | Claude invokes `factory` on change requests even without `/factory` |
| Workspace lookup | `SKILL.md` → Inputs | `/factory` | The descriptor is found in the repo or the nearest parent folder, so a module session uses the workspace factory |
| Module rules | `.claude/rules/modules/<area>.md` at the workspace root, generated by `pf rules sync` | When Claude touches files under that module (`paths:` glob) | Points to the module's `AGENTS.md` and `CLAUDE.md`, gates, test policy and owning Git target |
| Module install | `pf install module <path> --workspace <root>` | — | Copies both runtime kits into a module repo. Codex uses the installed `$product-factory` skill. Claude Code also receives the guard, always-on rule and attribution setting. A nested repo is its own Claude Code project, and skills are only found up to the repo root |
| Attribution policy | `vcs.attribution: none` → `"attribution": {"commit": "", "pr": "", "sessionUrl": false}` in `.claude/settings.json` | Every session | No AI trailer or line in commits and PRs |
| Memory read | `pf memory [--json] [--root]` | — | Lists the repo's auto memory. Location: `autoMemoryDirectory` (local, then project, then user settings), else `~/.claude/projects/<main checkout path, non-alphanumerics → '-'>/memory/` |
| Memory promotion | `/factory memory` (also inside `/factory init` and `/factory retro`) | — | Per-memory verdicts in `.factory/memory-review.md`. Approved team items become a docs job (PR or MR), approved personal items go to `CLAUDE.local.md`, and promoted or stale memories are deleted. Nothing happens without approval |

## Why memory needs promotion

Per Claude Code's docs, auto memory is machine-local and **is not loaded into
subagents**. All factory roles are subagents, so a convention that exists only in
auto memory is invisible to the engineer and the reviewers. The repo is the only
place every role, teammate and machine sees.

## Verification

- Unit: `descriptor` (the dialect and the shipped template), `rules` (rendering),
  `memory` (path sanitising matches Claude Code, frontmatter parsing), and
  `install` (attribution and hook merges).
- End to end, on a scratch workspace with two nested repos:
  - a workspace install with `--no-ai-attribution`;
  - `pf rules sync`;
  - `pf install module` for each child, which refuses unlisted paths;
  - `pf doctor` flagging an uninstalled module and passing once it is installed.

## Known limitations

- The rule and skill trigger are instructions, not enforcement. Claude can still
  answer a change request directly. The guard hook is the enforced part.
- The descriptor reader handles the factory's own YAML dialect, not general YAML.
- Rules sync covers `multi-repo` only. A single repo needs no module rules.

The installed `AGENTS.md` section routes change requests through the shared
coordinator in hosts that read project instructions. The installer adds a
Gemini context import and a pointer in existing Hermes-specific context
files, which Hermes reads before `AGENTS.md`. Native trust and account
settings remain managed by each host.

Project installation also generates path-scoped rules for workspace modules.
The sync checks that the target filenames belong to Factory before replacing
them. Use `pf rules sync` after changing module settings.
