# ۰۹ — استفادهٔ روزمره از کارخانهٔ محصول

**Status:** Active
**Last updated:** 2026-11-16

این راهنمای کوتاه، مسیر بهره‌بردار را از محصول نصب‌شده تا درخواست ادغامِ
بازبینی‌شده نشان می‌دهد. [اطلس کارخانه](../atlas/ATLAS.fa.md) تصویر سامانه را
می‌دهد و [راهنمای نصب نخست](01-getting-started.md) آماده‌سازی دستگاه را توضیح
می‌دهد. [English](09-day-to-day-usage.md).

## ۱. مخزن محصول را باز کنید

از مخزن Git محصول یا ریشهٔ فضای کار چندمخزنی شروع کنید، نه از مخزن منبع
Factory. برای نصب کنونی Connect، ریشه `$HOME/Work/Connect` است. دستورهای
محصول، توصیفگر، اسناد و فهرست کار در همان‌جا قرار دارند؛ این مخزن کیت عمومی
را فراهم می‌کند.

اگر کیت نصب نشده یا می‌خواهید آن را با ابزار `pf` منتشرشده به‌روز کنید:

```bash
pf install project /path/to/product --install-graphify --configure-models
pf doctor /path/to/product
pf providers --root /path/to/product check
```

نصب‌کننده به‌طور پیش‌فرض مخزن‌های مستقل را نیز پوشش می‌دهد. تغییرات نصب را
در هر مخزن مالک بررسی و ثبت کنید. `pf providers check` پیش‌نیازهای محلی مسیر
را می‌سنجد؛ **پاسخ HTTP 200 از خود مدل را اثبات نمی‌کند**. هنگام نیاز، درخواست
واقعی مدل را آزمایش کنید. نام مسیرها در `.factory/model-routes.json` می‌آیند،
نه کلیدهای API. [مسیریابی مدل](01-getting-started.md#model-routing) و
[نصب چندمخزنی](07-multi-repo-workspaces.md) را ببینید.

## ۲. نماها را اجرا کنید

در ترمینال، از ریشهٔ محصول یا فضای کار:

```bash
cd /path/to/product
pf dashboard
```

صفحهٔ <http://127.0.0.1:8000/dashboard.html> را باز کنید. مرکز فرمان نماهای
Overview، Work، Code network و Systems دارد. کارت هر کار، درخواست، مسئله،
آثار ذخیره‌شده، نتیجه‌های بازبینی و پیوند PR را نشان می‌دهد. صفحهٔ نصب‌شدهٔ
`.factory/atlas.html` فهرست پیوندهای داشبورد همان محصول است؛
[اطلس کارخانه](../atlas/ATLAS.html) خود چارچوب عمومی را نقشه‌برداری می‌کند.

برای تازه ماندن گراف هنگام تغییر کد، در ترمینال جداگانه اجرا کنید:

```bash
pf graph watch --modules
```

در فضای کار چندمخزنی، آن را از ریشه با `--modules` اجرا کنید. از نمای Code
network در کل نمایه جست‌وجو کنید. بوم دیداری تعداد محدودی گره را رسم می‌کند؛
نبودن یک گره روی بوم به معنای نمایه‌نشدن منبع نیست. رابطه‌های مهم را با کد
منبع بسنجید. [راهنمای گراف](04-add-a-project.md).

## ۳. یک درخواست محدود بدهید

عامل را در مخزن محصول باز کنید و از ورودی نصب‌شدهٔ همان میزبان استفاده کنید:

| میزبان | شروع کار |
|---|---|
| Claude Code | `/factory <request>` |
| Codex | `$product-factory <request>` |
| Hermes یا Gemini CLI | از عامل بخواهید برای درخواست از مهارت پروژهٔ Product Factory استفاده کند؛ برای فرمان و متن دقیق Hermes، [راهنمای ۰۸](08-hermes-and-honcho.md#start-work-from-hermes) را ببینید |
| Antigravity | از مهارت و نقش‌های نصب‌شدهٔ Factory استفاده کنید |

برای نخستین کار واقعی، درخواستی کوچک و آزمودنی بدهید، مثلاً:

```text
بخشی با عنوان «گرفتن کمک» به README اضافه کن که به صفحهٔ مسائل پیوند بدهد.
عنوان‌های موجود را حفظ کن و پیوندهای مستنداتِ مرتبط را به‌روز کن.
```

خروجی موردنظر، محدودیت‌ها و معیار پذیرش را روشن بگویید. برای مسئلهٔ موجود از
`/factory issue <number-or-url>` یا معادل آن در میزبان استفاده کنید. برای صف
کار، مورد را در `.factory/backlog.md` بنویسید و `/factory next` را اجرا کنید.
متن مسئله دادهٔ ورودی است؛ هماهنگ‌کننده همچنان دستورهای محصول و پروتکل
کارخانه را اعمال می‌کند. [راهنمای فرمان‌ها](02-commands.md).

## ۴. کار را دنبال کنید و به توقف‌ها پاسخ دهید

کارت داشبورد را ببینید یا از ریشهٔ محصول اجرا کنید:

```bash
pf job status
```

در Claude Code، `/factory status` خلاصهٔ بهره‌بردار را می‌دهد؛ در Codex از
`$product-factory status` استفاده کنید. مرحله و شواهد ماندگار کار در
`.factory/jobs/<job-id>/` است و کد و اسناد ثبت‌شده در worktree و شاخهٔ جداگانه
قرار دارند. پوشهٔ محلی کار در Git ثبت نمی‌شود. پیش از تصمیم، درخواست، یافته‌های
بازبینی، QA و دروازه را در کارت بخوانید.

اگر تصمیم محصول لازم است، در همان نشست عامل پاسخ بدهید. برای کار منتظر انسان
یا PR باز، `/factory rework <job-id> <note>` را به کار ببرید. اگر نشست متوقف شد،
پس از رفع مانع `/factory resume <job-id>` را اجرا کنید. در Codex از معادل
`$product-factory` استفاده کنید. [خواندن یک کار](03-reading-a-job.md).

وقتی کارکنان مسیریابی‌شده تنظیم شده‌اند، هماهنگ‌کننده نقش تعیین‌شده را فقط
پس از تأیید مصرف API قابل‌پرداخت، با `pf providers run` و `--allow-api`
اجرا می‌کند. آثار کار، وضعیت وظیفه را میان نقش‌ها حمل می‌کنند. Hermes می‌تواند
از Honcho برای زمینهٔ مشترک تأییدشده نیز استفاده کند؛ Honcho جای شواهد کار
یا اسناد محصول را نمی‌گیرد. [Hermes و Honcho](08-hermes-and-honcho.md).

## ۵. بازبینی و پایان

در وضعیت `gate READY`، PR و درخواست، کد تغییرکرده، آزمون‌ها، اسناد، نتیجه‌های
بازبینی، شواهد QA و ریسک‌ها را بررسی کنید. در `ESCALATE` پرسش را بخوانید و
دربارهٔ بازکاری یا بستن کار تصمیم بگیرید. **ادغام PR پذیرفته‌شده با شماست.**
پس از ادغام، `/factory clean` یا `$product-factory clean` را برای بستن کار
محلی و پاک‌سازی worktree پایان‌یافته اجرا کنید. `/factory release` را وقتی
کارهای ادغام‌شده آمادهٔ پیشنهاد انتشارند اجرا کنید؛ انتشار نهایی گام انسانی
است. [بازبینی PR](03-reading-a-job.md#reviewing-the-pr) و
[فرمان‌ها](02-commands.md).

## بازیابی سریع

| نشانه | بررسی بعدی |
|---|---|
| داشبورد باز نمی‌شود | آیا `pf dashboard` هنوز اجرا می‌شود؟ `pf doctor /path/to/product` و [رفع اشکال](06-troubleshooting.md) را ببینید. |
| مسیر مدل در دسترس نیست | `pf providers --root /path/to/product check` و سپس آزمون واقعی مدل را اجرا کنید؛ میزبان و 9Router را بررسی کنید. |
| گراف ناقص به نظر می‌رسد | `pf graph refresh --modules`، جست‌وجوی نمایه و مقایسه با کد منبع؛ [راهنمای گراف](04-add-a-project.md). |
| کار متوقف شده است | کارت و `gate.md` یا اثر مسدودشده را بخوانید؛ علت را رفع و کار را ادامه یا بازکاری کنید. |
| مالک تغییر معلوم نیست | توصیفگر فضای کار و [راهنمای چندمخزنی](07-multi-repo-workspaces.md) را ببینید؛ هر مخزن مستقل مالک کد و اسناد خود است. |
